# Консоль рядом с сайтом stroppy.io

Часть stroppy-cloud в общем решении «сайт и консоль как один продукт». Часть
сайта — `stroppy-io.github.io/plans/site-redesign.md`.

## Решение

- stroppy.io (Docusaurus) — публичный сайт: лендинг, мега-меню, доки, блог,
  страница How it works. cloud.stroppy.io — консоль. Два деплоя, один
  домен второго уровня.
- У консоли нет своего лендинга. Гость на `cloud.stroppy.io/` уходит на
  stroppy.io.
- Мега-меню есть только на сайте. Кит остаётся каким есть: токены, CSS,
  шрифты, лого, chart. Компонентов шапки и `nav.json` в нём нет.
- Публичное лицо консоли — экраны входа и онбординга: `/login`, `/register`,
  `/recovery`, `/verify`, `/auth/error`, `/welcome`, `/tenants/new`.
  Сверху у них простая полоса на токенах кита: лого → stroppy.io и «Back to
  site». Страницы данных (`/leaderboard`, `/s/$token`) получают ту же полосу.
  `/embed/*` остаются без шапки, это iframe. Внутри `/t/$slug` и `/admin`
  остаётся своя шапка консоли, лого в ней ведёт на stroppy.io.
- Доки Cloud для пользователя пишутся на сайте отдельным разделом без
  версий. Консоль ссылается на них через «?». Внутренние доки (`docs/`,
  `AGENTS.md`, `STROPPY.MD`) остаются здесь.

## Этап 1. Консоль рядом с сайтом

1. **Лендинга нет.** Удалить `/land`, `/how` и `web/src/components/landing/*`,
  кроме того, что нужно полосе и публичным страницам. `/` для гостя
  редиректит на `https://stroppy.io/`, со старых адресов тоже редиректы:
  `/land` → stroppy.io, `/how` → страница How it works на сайте. Адрес
  сайта задаётся конфигом сервера (`PublicConfig`), в коде не зашит.
2. **Полоса публичных экранов.** Лого → stroppy.io, «Back to site», справа
  переключатель темы. На токенах `--st-*`, без `@grafana/ui`. Экраны входа и
  онбординга перевести на стили кита, чтобы человек с сайта не попадал
  «на другой сайт».
3. **Тема.** По умолчанию тема следует системе (сейчас по умолчанию тёмная,
  `web/src/app/theme-context.tsx`). Выбор хранится в cookie на `.stroppy.io`,
  так что переключатель общий с сайтом. Имя cookie и значения
  (`light|dark|system`) согласуются с сайтом.
4. **Сессия видна сайту** (`deployments/kratos/kratos.yml`, прод-оверлей):
   - `session.cookie.domain` и `cookies.domain` = `.stroppy.io`;
   - `serve.public.cors`: origin `https://stroppy.io`,
     `allow_credentials: true`. Тогда сайт делает
     `GET https://cloud.stroppy.io/v1/sessions/whoami` с credentials и
     показывает «Sign in» или «Open console»;
   - `allowed_return_urls` += `https://stroppy.io`;
   - выход из консоли ведёт на stroppy.io.
5. **Публичный API для сайта.** `http.public_cors_origins` по умолчанию уже
  `https://stroppy.io` (`cmd/stroppy-cloud/application/config.go`).
  Проверить значение на проде. Сайт читает `/api/v1/public/rating` и
  `/api/v1/public/catalog`. Строку «движки × версии × топологии» сайт
  считает из каталога, нового эндпоинта не нужно.
6. **Ссылки «?»** с экранов консоли на раздел Cloud сайта. Базовый адрес
  доков задаётся тем же конфигом, что и адрес сайта.

Контракт меняется только если адрес сайта и доков приходит в
`PublicConfig`. Тогда этап выходит минорным релизом.

## Этап 2. Вход через GitHub

Регистрация открыта: через GitHub и по почте с паролем. Kratos v26.2.0
умеет GitHub сам (`provider: github`).

- **Kratos.** Метод `oidc`, провайдер `github`, `scope: [user:email]`.
  Kratos берёт основную подтверждённую почту из `/user/emails`, даже если
  в профиле она скрыта. Callback:
  `https://cloud.stroppy.io/v1/self-service/methods/oidc/callback/github`.
  Он идёт через наш прокси `/v1`, и `serve.public.base_url` его уже
  покрывает.
- **Маппер** (`deployments/kratos/github.jsonnet`): `email` из claims,
  `name` = имя, а если его нет — логин. Почта помечается подтверждённой
  через `verified_addresses`, поэтому гейт на `email_verified` (инвайты,
  админство, будущий free tier) проходит сразу.
- **Схема identity** не меняется: расширение схемы Kratos v26 не знает
  `credentials.oidc` и не стартует с ним.
- **Регистрация открыта двумя путями:** GitHub и почта с паролем
  (полный цикл: код подтверждения письмом, восстановление пароля кодом).
  На `/register` и `/login` кнопка GitHub стоит над формой.
- **Связка аккаунтов.** Если человек с такой почтой уже входил паролем,
  Kratos предлагает связать аккаунты, войдя старым способом. Экрану входа
  нужно показать этот шаг. Проверить поведение v26 по доке.
- **SPA.** Кнопка «Continue with GitHub» на `/login` и `/register` из
  `ui.nodes` группы `oidc`. Отправка обычной HTML-формой, не `fetch`,
  потому что дальше идёт редирект на GitHub. Ошибки провайдера — на
  `/auth/error`.
- **Объём:** 1–2 дня и живая проверка на стенде и на проде.
- **От людей:**
  - GitHub OAuth App в org stroppy-io: Homepage `https://cloud.stroppy.io`,
    callback выше. Для локального стенда отдельный App с callback на
    `http://localhost:18347/v1/...`;
  - client id и secret в секреты прод-деплоя. Kratos читает их из env
    `SELFSERVICE_METHODS_OIDC_CONFIG_PROVIDERS`.

Вход через Yandex — позже, тем же путём (generic OIDC).

## Этап 3. Free tier (бэклог)

В бэклоге: не входит в v0.6.0, делается отдельным минорным релизом.

Один прогон в сутки на тенант, на нашем облаке, на минимальной базе любого
движка. Обход через создание новых тенантов пока допустим.

**Что такое «маленький» прогон.** Пресет: одна машина базы, single-node,
минимальный размер (2 vCPU / 8 ГБ, небольшой `network-ssd`), авто-тюнинг,
одна машина раннера на 2 vCPU. Нагрузка — TPC-B или TPC-C на малом
масштабе: загрузка ~1–2 мин, прогон 3–5 мин. Сейчас single-node PG в
матрице занимает 18–20 мин, из них инфраструктура ~6–7 мин (машины ~3,
развёртывание ~2, отчёт и снос ~1–2), остальное — TPC-C с 10-минутным
прогоном. С пресетом выходит 11–14 мин от запуска до отчёта. Кластерные
движки (CockroachDB, YDB, Picodata) в минимальном single-виде
разворачиваются дольше — время по каждому пресету проверить живым прогоном.

**Что нужно в продукте:**
1. Профиль провайдера, принадлежащий платформе (наш YC), которым тенант
   пользуется без своего профиля. Сейчас профиль принадлежит тенанту
   (`provider.Profile.TenantID`), ключи облака лежат секретом
   `provider-<id>` в пространстве Graphene тенанта, и пайплайн прогона
   берёт их оттуда. Бесплатные прогоны идут в отдельном пространстве
   платформы, а не копией наших ключей в каждый тенант: тенант читает свои
   секреты, отдавать ему ключ от нашего облака нельзя. Значит, прогон,
   его события, логи, метрики и отчёт должны уметь жить в пространстве
   платформы и показываться в тенанте. Сеть готова: с v0.5.0 одна VPC на
   профиль и подсети на прогон.
2. Лимит на допуске (admission): 1 бесплатный прогон в сутки на тенант и
   общий лимит одновременных бесплатных прогонов. Лимит защищает бюджет
   облака.
3. Ограничения на сервере, не в форме: только пресеты (каталог
   `/examples`), без «keep stand», без своих образов, без `external`, с
   дедлайном прогона. При превышении дедлайна — отмена и снос. Общего
   дедлайна у прогона сейчас нет; он нужен и обычным прогонам.
4. Бесплатный прогон запускается только с подтверждённой почтой. После
   регистрации паролем сессия выдаётся сразу, а почта подтверждается позже.
   При входе через GitHub почта подтверждена сразу.
5. Выключатель free tier в админке, запись в аудит.
6. Онбординг: шаг «запустить пример на нашем облаке» рядом с «подключить
   свой облачный аккаунт». `/examples` остаётся внутренней страницей и
   служит источником пресетов (клон — `POST /api/v1/t/{slug}/examples/{id}:clone`).
7. В контракте новые значения: вид профиля, причина ожидания или отказа
   «бесплатный лимит», лимиты. Значит, минорный релиз.

**Объём:** 1,5–2 недели и живая проверка на YC. Самые дорогие части —
профиль и пространство платформы и ограничения на сервере.

**Решить людям до начала:** бюджет и лимиты (одновременные бесплатные
прогоны, потолок в день на платформу), облако и папка YC с отдельными
квотами, список пресетов (все движки single-node или сначала PostgreSQL,
MySQL, OrioleDB).

## Проверить до обещаний на сайте

- **Своя база (`external`).** В консоли есть kind `external` («External
  database», DSN и протокол). Мы поднимаем только раннер, раннеру нужен
  профиль провайдера тенанта. Метрики базы есть для PostgreSQL и MySQL,
  авто-тюнинга нет. Прежде чем сайт обещает «Point Stroppy at your
  database», нужен один живой прогон на YC.

## Бэклог

- **Своё железо или раннер у клиента.** Агент ставится одной командой
  `docker run` и подключается к серверу. Новый сценарий, прорабатывается
  отдельно.
- **DSN своей базы как секрет.** Шифрование при хранении (сейчас JSON в
  `library`, `internal/infrastructure/postgres/repositories/library.go`),
  секрет вместо env в RunSpec, маскирование в логах. Сделать до того, как
  `external` станет массовым сценарием.
- Вход через Yandex.
- Письма Kratos (код подтверждения, восстановление пароля) в стиле кита.
- Аналитика воронки: инструмент выбирают люди, плюс серверная отправка
  событий (регистрация через webhook Kratos, `tenant.create`,
  `provider.create`, первый `run.launch`, первый `result.published`).
- `/api/v1/public/stats`: число публичных прогонов и часы прогонов для
  hero, если строки из каталога окажется мало.

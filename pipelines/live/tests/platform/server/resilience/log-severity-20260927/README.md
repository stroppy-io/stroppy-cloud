# Graphene: фильтр уровня теряет записи с числовой severity

Статус: **исправлено в раскатанной 0.2.26; подтверждено через сервер**.
В одном фиксированном окне без фильтра, с ERROR и с WARN/ERROR возвращаются
одни и те же 10 записей. [Проверка](../graphene-0.2.26/verification.json).
Ниже сохранены исходное воспроизведение и требования к исправлению.
Это не прежний отказ публикации pipeline: тот закрыт успешным resync и свежими
квотами. Пайплайны выполняются. По правилу владельца дальнейшая приёмка
приостановлена при обнаружении дефекта, требующего правки Graphene.

## Воспроизведение через Stroppy Cloud

Namespace: `t-server-live-20260924`.
Run: `0c3d8b9e-2c1c-4547-9dc8-fe2b7f656054`.
Время записей: 2026-09-27 16:08–16:14 UTC.

1. `GET /api/v1/t/server-live-20260924/runs/0c3d8b9e-2c1c-4547-9dc8-fe2b7f656054/logs?q=activity%20failed&limit=3`
   возвращает HTTP 200 и три записи `level=error`, `severity_number=17`.
2. Тот же запрос с `level=error` — HTTP 200 и **пустой список**.
3. Через `/logs:raw`, с одинаковым окном 16:08:00–16:14:30 UTC:
   `severity_number:="17"` возвращает три записи;
   `(severity:in("ERROR") OR severity_text:in("ERROR"))` — ни одной.
4. Фильтр `level=info` работает для других записей. Facets также показывает
   наличие error/warn. Проблема не в отсутствии логов или общем доступе к ним.

Доказательства: [без фильтра](unfiltered.json), [с error](filtered-error.json),
[с info](filtered-info.json), [числовое поле](raw-numeric.json),
[текстовые поля](raw-text.json), [facets](facets.json).
Все запросы идут через сервер; прямых обращений к хранилищам телеметрии нет.

## Причина в исходниках Graphene

Тег `v0.2.25`, `cc6e3f1706da8e103f08b5ccfaabffa0d6b6131b`:

- `internal/telemetry/logsql.go`, `selection`, строки 107–114: фильтр severity
  строится только по `severity` и `severity_text`. Регистр уже нормализуется
  через `strings.ToUpper`.
- Там же `parseLogsQLStream`, строки 267–269: при отсутствии текстовой severity
  читатель использует `severityFromNumber(fields["severity_number"])`.
- `severityFromNumber`, строки 279–299: значения 17–20 преобразуются в ERROR.

Следствие: читатель показывает запись как ERROR, но собственный typed filter
Graphene не может её найти. Это подтверждено отдельными raw-запросами в одном
временном окне, а не только статическим предположением.

Первичная гипотеза про lowercase на стороне Stroppy Cloud **отброшена**:
пробная нормализация на сервере не изменила результат; Graphene уже делает её.
Пробная правка и её тест удалены. SHA исходников сервера снова совпадает с
проверенным набором 19 интеграционных / 7 race тестов:
`11c62ebc5c800f5e9b6e8c8ff816e5800faa3e4ff9631e0d815971368a16f441`.
Server-side обход через raw query не добавлен.

## Требуемая правка

Согласовать severity-selection с нормализацией записей при чтении: одинаковые
правила для текстовых полей, их регистра и fallback на числовую OTel severity.
Числовая ветка должна соблюдать ту же семантику, что reader, включая границы
диапазонов. Сохранить изоляцию namespace/run и AND с остальными фильтрами.
Проверить согласованность исторического чтения, live tail и facets.

Приёмка:

- Чисто числовые severity: DEBUG 5–8, INFO 9–12, WARN 13–16, ERROR 17–20,
  FATAL 21–24; отдельно unspecified/отсутствующее поле.
- Текстовые записи и смешанные варианты; согласованный приоритет полей.
- В одном фиксированном окне записи, полученные без фильтра и отображаемые как
  ERROR, присутствуют с typed severity ERROR; multi-select WARN/ERROR даёт
  объединение, не теряет записи при пагинации.
- Реальная проверка на указанном run через сервер: `level=error` возвращает
  сохранённые activity failures. Изоляция чужих run/namespace сохраняется.

Graphene не изменялся. Логи показывают отдельную сетевую проблему:
TLS handshake timeout при pull `quay.io/prometheus/node-exporter:v1.12.1` на
runner. Это причина остановки аналитического прогона до workload, а не
следствие severity-фильтра. Docker Hub `prom/node-exporter:v1.12.1` доступен
для чтения и имеет тот же manifest digest; заменённый запуск ещё не выполнялся.

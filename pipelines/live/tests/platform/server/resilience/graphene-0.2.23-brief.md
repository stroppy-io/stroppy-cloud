# Устойчивость сервера: блокер Graphene 0.2.23

Статус: **приёмка остановлена на контракте запуска и проверки существования run**.
Нельзя утверждать отсутствие дублей при потере ответа и автоматическом повторе.
AWS и UI не входят в эту проверку.

Основание — чтение исходников точного тега `v0.2.23`, commit
`1167739449969507c4e6292c51baa840350d5d3c`, с чистой рабочей директорией Graphene.
[Машинное доказательство](graphene-source-audit.json) содержит фрагменты, номера
строк и SHA-256 файлов. Это **статический разбор, не воспроизведённый инцидент
на кластере**. Повторы платных запусков для демонстрации дублей не выполнялись.
Код и конфигурация Graphene не изменялись.

## Бриф для Graphene

### 1. `GetRun`: отсутствие run нельзя отличить от сбоя Temporal

Места в Graphene:

- `internal/services/management.go:269`, `Management.GetRun`;
- `internal/services/workerplane.go:266`, `WorkerPlane.GetRun`.

После `DescribeWorkflowExecution` **любая** ошибка превращается в
`status.Error(codes.NotFound, err.Error())`. В эту ветку попадают и недоступность
Temporal, и таймаут. Теряется тип ошибки, необходимый для восстановления.

Что требуется:

- `NotFound` только для подтверждённого отсутствия workflow;
- `Unavailable`, `DeadlineExceeded`, `Canceled`, ошибки прав и остальные ошибки
  сохраняют соответствующий смысл в management и worker API;
- клиент не должен разбирать текст ошибки для определения существования run;
- если запуск уже принят, но ещё находится в очереди, контракт проверки его
  существования должен учитывать это состояние (см. пункт 3).

Приёмка: таблица тестов `DescribeWorkflowExecution` → ошибка API для NotFound,
Unavailable, DeadlineExceeded, Canceled, PermissionDenied и неизвестной ошибки.
На интеграционном стенде существующий run при недоступном Temporal не должен
выглядеть отсутствующим; после восстановления возвращается тот же run.

### 2. Повтор `StartRun` не гарантирует одно исполнение

Места в Graphene:

- `internal/services/management.go:181`, `startRunCore`;
- `internal/services/management.go:125`, `fireRun`;
- `internal/pipelineflow/pipelineflow.go:266`, обработчик `FireCmd`;
- `internal/worker/worker.go:324`, `FirePipeline`.

Для открытого workflow выставлен `USE_EXISTING`, но для завершённого —
`ALLOW_DUPLICATE_FAILED_ONLY`. Это допускает новое Temporal-исполнение под тем же
`run_id` после failed/canceled/terminated/timed-out. Обработчик `FireCmd` передаёт
повтор дальше; отдельной проверки уже принятого запроса по `run_id` в нём нет.

Опасная последовательность:

1. Сервер отправляет запуск A; Graphene принимает его, ответ теряется.
2. A успевает завершиться с ошибкой или отменой.
3. Сервер восстанавливается и повторяет запрос с тем же ID. В частности,
   ошибочный `NotFound` из пункта 1 может заставить его считать A отсутствующим.
4. Политика Graphene допускает новое исполнение A. У сервера остаётся одна
   запись для нескольких исполнений: результаты, события и ресурсы становятся
   неоднозначными.

Проверка `GetRun` перед повтором снижает риск, но не заменяет атомарной гарантии
на принимающей стороне: первый запрос может ещё обрабатываться между проверкой
и повторной отправкой. Локальный `Idempotency-Key` сервера предотвращает создание
второй строки PostgreSQL, но сам по себе не предотвращает второе исполнение.

Требуемый контракт:

- `(namespace, run_id)` определяет одно логическое исполнение во всех состояниях;
- повтор того же запроса возвращает уже принятое исполнение/операцию без запуска
  новой работы, включая failed/cancelled/completed и состояние queued;
- другой pipeline или параметры под занятым ID дают явный конфликт;
- полный re-run создаётся с **новым** ID; resume здесь не требуется;
- защита должна действовать и при повторе внутренней start activity после потери
  ответа Temporal или ошибки запуска worker-контейнера;
- срок хранения ключа/принятого запроса и поведение после удаления должны быть
  явными: одного Temporal retention недостаточно для бессрочного обещания.

Выбор механизма за Graphene: запрет повторного использования workflow ID — часть
решения, но также нужны корректный ответ на повтор и защита до фактического
старта workflow, включая очередь. Одной заменой enum вся задача не закрывается.

Приёмка: одинаковый запрос одновременно, после потери ответа и после каждого
терминального состояния; потеря ответа между Temporal start и подтверждением
start activity; перезапуск Graphene между принятием запроса и стартом. Для всех
случаев — одно исполнение, один набор ресурсов, неизменный результат. Отдельно
проверить конфликт payload и независимость одинаковых ID в разных namespaces.

### 3. Уточнить ответ о принятом, но поставленном в очередь запуске

Связанный риск для `queue`-политики, не утверждение о текущей конфигурации
Stroppy-пайплайнов: `FireCmd` сохраняет `st.Pending = &fire`, а `fireRun` возвращает
`FailedPrecondition`, если `RunId` в ответе отсутствует. Это не гарантированный
отказ: работа может стартовать позже. Кроме того, Pending содержит один слот.

Нужно явно определить `accepted/queued/rejected`, стабильную идентичность
принятого запроса и судьбу предыдущего queued-запроса при новом. Повтор A не
должен создавать ещё одну работу или незаметно заменять B. Если очередь
намеренно объединяет запросы, вытеснение должно быть наблюдаемым результатом.
Ошибки ожидания `FirePipeline` также нельзя безусловно объявлять окончательным
`FailedPrecondition`: принятие могло произойти до потери ответа.

Приёмка: A занят, B принят в очередь, ответ B теряется; повтор B и новый C.
У каждого запроса должен оставаться однозначный, доступный клиенту исход.

## Что остаётся исправить в Stroppy Cloud

Эти дефекты выявлены чтением кода, пока не исправлены и не закрыты fault-тестами:

- `internal/domain/run/service.go:356` и
  `internal/domain/suite/service.go:478`: любая ошибка StartRun сразу переводит
  сохранённые строки в failed. При потерянном ответе принятый запуск может
  продолжать работу без наблюдателя. Нужна долговечная доставка сохранённого
  запуска с тем же ID, различающая отказ и неизвестный исход; suite запускается
  целиком, её дети не должны повторно стартовать по отдельности.
- `internal/domain/run/projector.go:229`: ошибка RunClose только логируется
  после записи terminal status. Для terminal run без keep нет следующей попытки
  получить результат. Нужен сохраняемый признак незавершённой финализации и
  повтор получения/сохранения результата, включая пустой результат и partial.
- `internal/domain/suite/projector.go:146`: при финализации suite любая ошибка
  запроса статуса дочернего run трактуется как отсутствие и может ошибочно
  завершить его запись. Нужен достоверный NotFound и повтор при временных сбоях.
- Отмена сохраняет cancelling перед RPC, но проектор пока не доставляет
  потерянный запрос отмены повторно. Нужны тесты отказа до и после принятия cancel.
- Текущий fakeGraphene возвращает AlreadyExists для **любого** повторного ID.
  Эта модель строже реального контракта 0.2.23 и не доказывает защиту от описанного
  повторного исполнения. Fault-тесты должны отражать реальную границу.

После исправления Graphene — сначала локальные fault-тесты и исправления сервера,
затем сбой только локального соединения server→Graphene, перезапуск сервера во
время suite, повтор HTTP с тем же ключом, автоматический keep expiry и обновление
YC-токенов. Подтверждать не только статусы, но и идентичность исполнения, результаты,
артефакты и отсутствие оставшихся стендов через сервер.

непокрытые механизмы через сервер. Исторический passed не равен новой приёмке
через API; unknown не равен failed.

но её observer-restart и конкурентные HTTP-тесты не закрывают неоднозначный исход
server→Graphene StartRun и все случаи потери финального результата.

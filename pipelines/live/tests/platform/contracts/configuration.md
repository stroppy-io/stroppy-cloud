# Конфигурация стенда и теста

Источник форм — schemapb в `pipelines/schemas`; экспорт для UI лежит в
`web/src/schemas`. Форма не должна самостоятельно воспроизводить дефолты и
ограничения: сервер возвращает effective configs, итоговый RunSpec и Fit.

## Входы и приоритет

1. Топология БД и выбранные XS/S/M/L/XL дают рабочую основу.
2. `sizes.<role>.disk` меняет размер/тип стандартного data-диска.
3. `sizes.<role>.machine` (`test.machine@1`) переопределяет CPU, RAM, образ,
   зону, platform/instance type, labels, boot disk, список дополнительных
   дисков с типом/размером/block size, ext4/XFS и mount options, гарантированную долю CPU, preemptible и public IP.
4. `database.runtime` (`test.runtime@1`) меняет рецепт развертывания БД.
5. `test.execution` (та же схема) задаёт окончательные настройки конкретного
   теста, включая отдельные машины по имени. Эти значения попадают в snapshot
   и повторный запуск.

`runtime.machines` — имя машины → настройки. `runtime.containers` — список
селекторов `name`/`role` и объекта `set`. При двух селекторах применяется их
пересечение. Порядок списка определяет приоритет; отсутствие совпадения —
ошибка. Ролевой селектор включает exporters этой роли: для изменения только БД
используйте имя контейнера из предпросмотра RunSpec.

Контейнер можно настроить целиком в пределах исполняемого контракта:
образ, entrypoint, argv, env, порты host-network, mounts, содержимое файлов,
healthcheck, restart, ulimits, dependencies и scrape endpoint.
`additional_containers` добавляет свои контейнеры. `host_prep`, `scrapes`,
`flows` добавляются к рецепту. `network`, `observability` и
`result_expectations` изменяют соответствующие настройки запуска.
`workload` позволяет переопределить окончательный endpoint/driver/segments,
например при изменении порта или учётных данных в собственном конфиге БД.

Отсутствующее поле сохраняет основу. Явные `false`, `0`, пустая строка и пустой
список имеют собственный смысл. Объекты объединяются по ключам, пустой объект
очищает объект. Списки заменяются, кроме непустого `files`: они объединяются
по абсолютному пути, и пользовательское содержимое полностью заменяет файл
по этому пути. `files: []` удаляет сгенерированные файлы. `healthcheck: null`
убирает проверку. Никакой новый ключ не должен молча игнорироваться.

Например, это часть TestWrite, не полный запрос:

```json
{
  "sizes": {
    "db": {
      "size": "S",
      "machine": {
        "cpu": 8,
        "memory_gb": 32,
        "boot_disk": {"gb": 80, "type": "network-ssd"},
        "disks": [
          {"name": "data", "gb": 200, "type": "network-ssd", "mount": "/data"},
          {"name": "wal", "gb": 93, "type": "network-ssd-nonreplicated", "mount": "/wal"}
        ]
      }
    },
    "runner": {"size": "S", "machine": {"cpu": 4, "memory_gb": 8}}
  },
  "execution": {
    "machines": {"db-1": {"preemptible": false}},
    "containers": [{
      "role": "db",
      "set": {"env": {"EXPERIMENT": "custom-storage"}}
    }]
  }
}
```

Выделенный WAL-диск монтируется на хосте, но размещение WAL на нём требует
соответствующего container mount и конфигурации самой БД. Добавление диска
само по себе не переносит данные.

YC создаёт принадлежащий run NAT gateway и route table, если хотя бы одна VM
не имеет публичного адреса: агент и загрузка образов требуют исходящей связи.
Эти ресурсы удаляются вместе со стендом.

## Нагрузка

`workload.stroppy@1` и `workload.segment@1` остаются основой настройки теста:
9 workload IDs, параметры конкретного сценария, SQL/schema overrides,
файлы или artifact refs, load workers, VUs, executor, duration/iterations,
query timeout, общий timeout, seed, steps/no_steps, thresholds, драйвер и
пулы соединений. Экспорт TPS и других измерений делает Stroppy.
`warmup` в текущем контракте — пауза перед сегментом, а не генерация нагрузки.

## Проверки и дефолты

- Невозможные формы, неизвестные поля и несовпавшие селекторы отвергаются.
- Проверяются известные сочетания YC platform/CPU/RAM/core fraction,
  гранулярность SSD по 93 GiB, addressability диска при заданном block size,
  уникальность дисков/точек монтирования, безопасные канонические пути,
  конфликты портов на одной машине и ссылки host preparation.
- Если размер data-диска не задан, пресет увеличивается до расчётного бюджета
  встроенного workload. Явный размер сохраняется и проверяется.
- Оценка исходных данных: TPC-C — 0.1 GiB/warehouse, TPC-B — 0.015 GiB/branch,
  TPC-H — SF GiB, TPC-DS — max(SF, 0.25) GiB из-за фиксированных dimensions;
  baseline — 256 bytes/row как плановый бюджет. Семейства могут сосуществовать,
  повтор одного семейства берёт максимальный размер.
- Рекомендация диска — `ceil(3 × estimated_data_gib + 2)` для данных,
  индексов/WAL/temp. Для быстрых SSD дефолт округляется вверх до 93 GiB. Встроенная оценка выше 80% доступного диска — блокирующая
  ошибка планирования; между ней и рекомендуемым размером — предупреждение.
  Это модель запаса, а не точный физический размер или доказательство границы
  сжатия. Большой SF и маленький диск отсекаются до provision.
- Проверяется диск под writable bind БД; чужие диски и диски runner не добавляют
  ей вместимость. Без подходящего data-диска учитывается boot disk минус
  10 GiB для ОС. Для distributed storage доступная сумма проверяется до учёта
  replication; отдельное предупреждение требует дополнительного запаса.
- Распознаваемые fixed buffer settings PostgreSQL/MySQL/MariaDB в окончательных
  файлах не могут превышать RAM. Эта проверка не является полной проверкой
  синтаксиса/семантики произвольного файла движком БД.
- Неизвестный объём произвольного SQL, external/managed storage без известного
  лимита и неизвестная платформа явно помечаются как непроверенные.
- Квоты CPU/RAM, числа VM/disks и известных классов YC-дисков проверяются по
  финальному RunSpec с загрузочными и дополнительными дисками. Отдельная
  квота Compute Optimized учитывает только машины `highfreq-*`; быстрый SSD
  использует `compute.ssdIOM3Disks.size`. Нулевая квота блокирует потребление
  соответствующего ресурса. Это не
  резервирование квоты: конкурентный запуск может изменить её остаток.

Известные ограничения сверены с
[YC CPU/RAM](https://yandex.cloud/en/docs/compute/concepts/performance-levels)
[YC disks](https://yandex.cloud/en/docs/compute/concepts/disk) и
[YC quotas](https://yandex.cloud/en/docs/compute/concepts/limits).
Они описывают локальный снимок возможностей; доступность платформы/образа в
зоне и текущие квоты определяет облако. AWS не включён в живую проверку;
YC-only опции не должны превращаться в молча проигнорированные AWS поля.

## Проверка без сервера

```sh
cd pipelines
go run ./live/tools/preflight < path/to/run-input.json
```

Инструмент принимает **скомпилированный RunSpec**, применяет схему и resource
preflight, печатает оценки/предупреждения без содержимого конфигов и секретов.
Никаких ресурсов не создаёт. При ошибке завершается с ненулевым кодом.
Пайплайн выполняет те же проверки самостоятельно перед provision; suite
проверяет все ячейки до запуска первой.

Проверки в коде: `spec/overrides_test.go`, `spec/resources_test.go`,
`internal/domain/compile/runtime_test.go`, `internal/api/runtime_test.go`,
`cmd/stroppy-cloud/application/integration_runtime_test.go` и симулятор отказа
до инфраструктуры. Интеграционный тест использует настоящий PostgreSQL и
подставной Graphene; это не испытание новых комбинаций ресурсов на YC.

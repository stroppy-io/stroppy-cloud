# Контракт server / UI / pipeline

Контракт фиксирует интерфейс для параллельной разработки сервера, UI и
пайплайнов. Он не означает прохождение всех сценариев на реальном облаке.
Результаты испытаний БД находятся в единственной таблице `../../progress.csv`.
Новые сочетания дисков, XFS и private VM с NAT требуют отдельных испытаний YC.

## Источники истины и ответственность

| Область | Источник | Кто меняет |
|---|---|---|
| Поля, ограничения, дефолты, конфиги | `pipelines/schemas` | Владелец контракта pipeline |
| Компиляция библиотечного теста в RunSpec | `internal/domain/compile`, общий валидатор `pipelines/spec` | Владелец контракта pipeline |
| Исполнение, результаты, события | `pipelines/spec`, `pipelines/internal` | Владелец pipeline |
| HTTP API | `openapi/parts`, объединённый `openapi/openapi.yaml` | Серверный агент в пределах этой версии |
| Go HTTP-типы | Сгенерированный `internal/oas` | Только `make generate-go` |
| TypeScript HTTP-типы | `web/src/api/schema.d.ts` | Только `make generate-ts` |
| Типы и описания динамических форм | `web/src/schemas` | Только `make schemas-export` |
| Экранные сценарии, хранение, авторизация, представление результатов | Сервер и UI | Агент UI+Server |

Сервер вызывает общий compiler/validator. UI получает схемы через
`GET /api/v1/catalog/schemas/{schemaId}` и использует preview/validate API;
не копирует расчёты ресурсов, дефолты и ограничения в компоненты формы.
Runtime JSON имеет типизированную схему `test.runtime@1`, а не свободный набор
непроверяемых ключей. Новые поля запрещено тихо игнорировать.

Все API-ответы через API middleware содержат `X-Stroppy-Contract-Version`.
Версия также указана в `spec.ContractVersion`, OpenAPI
`info.x-pipeline-contract-version` и `contract.lock.json`. Git-коммит с этим
lock — воспроизводимая передаваемая ревизия; сборки сервера и pipeline должны
браться из одной ревизии. Отдельное опубликование релиза этим документом не
подразумевается. Наличие `@1` в schema ID не заменяет проверку версии контракта.

## Входы и жизненный цикл

Пресеты → настройки машины по роли → `database.runtime` → `test.execution` →
валидация окончательного RunSpec. Полный порядок, настройки VM/БД/нагрузки и
границы оценок описаны в [configuration.md](configuration.md).

- `POST /api/v1/t/{slug}/databases:preview` — несохранённая БД и effective configs.
- `POST /api/v1/t/{slug}/workloads:preview` — нормализованная нагрузка.
- `POST /api/v1/t/{slug}/tests:validate` — Fit, зависимости и оценка ресурсов.
- `PATCH /api/v1/t/{slug}/tests/{id}` — сохранить определение.
- `POST /api/v1/t/{slug}/tests/{id}:launch` — повторная проверка, квоты,
  snapshot и запуск. Значение `ready` не резервирует квоту облака.
- `GET /api/v1/t/{slug}/runs/{id}` — сохранённые настройки, RunSpec и результат.

Точные тела, статусы HTTP и дополнительные операции определяет OpenAPI.
[test-patch.json](test-patch.json) — исполняемый пример PATCH существующего
теста PostgreSQL из интеграционного fixture, не самодостаточное определение
облачного профиля. Имена машин/контейнеров в overrides берутся из рецепта.
Повторный запуск сохраняет настройки snapshot; отмена и удаление стенда
остаются отдельными операциями существующего API.

Один RunSpec использует один runner. Распределённый Stroppy на нескольких
runner и произвольная корректность SQL не обещаются.
Остальные ограничения — в [README.md](README.md#ограничения-которые-нельзя-обещать-в-ui).


## Подготовка и удаление cloud-профиля

Профиль требует предварительной настройки отдельным пайплайном
`stroppy-provider-config` (`spec.provider_config@1`). Сервер выполняет её при
создании/изменении/проверке профиля; `ready` означает завершение cloud verify и
настройки Crossplane. UUID профиля и namespace задают уникальный ProviderConfig.
`deleting` и `delete_failed` — состояния профиля, запрещающие новые запуски;
DELETE повторяет незавершённую очистку. Реквизиты сохраняются до её успеха.
Активные прогоны и сохранённые стенды блокируют изменение и удаление профиля;
пайплайн отдельно проверяет реальные Crossplane resources/usages.

Yandex-профиль владеет одной сетью: `network.kind=create` — пайплайн создаёт
`vpc.Network` `<ProviderConfig>-net` и при `public_ips: false` общий NAT
(`-nat`) с таблицей маршрутов (`-routes`, 0.0.0.0/0 → NAT); `existing` —
сеть пользователя (`network_id`, необязательный `route_table_id`), ничего не
создаётся. Удаление профиля сначала удаляет эти объекты (после проверки, что
подсетей прогонов не осталось), затем ProviderConfig. Прогон создаёт в сети
профиля только свою группу безопасности и по подсети на зону; блоки подсетей
сервер выделяет из `network.pool_cidr` профиля при допуске из очереди и
записывает в `network.subnets` RunSpec. Профиль, настроенный до сети профиля,
сервер настраивает заново, пока его прогоны ждут в очереди (`provider`).

## Телеметрия через Graphene

Контракт рассчитан на Graphene 0.2.27, pipeline SDK 0.2.13 и Docker library
0.3.4. Сервер читает логи/метрики только через
Observe API Graphene 0.2.23+, передавая namespace и run ref. Адреса хранилищ
и их реквизиты не входят в настройки сервера. При отсутствии явного OTLP
override исполнитель разрешает локальный адрес Graphene на машине;
конфиг Stroppy получает его при запуске. Отдельная миграция тестов не нужна.
Курсоры логов непрозрачные; клиент не разбирает их как timestamp.
Grafana-session API недоступен до поддержки со стороны Graphene.

## JSON и редактор формы

- Отсутствие поля сохраняет основу. `false`, `0`, `""`, `[]`, `{}` и допустимый
  `null` имеют отдельный смысл; нельзя подменять их через `value || default`.
- Объекты overrides сливаются по ключам; пустой объект очищает объект.
  Массивы заменяются, кроме непустых `files`, объединяемых по абсолютному пути.
- Содержимое файла сохраняется побайтно после JSON-декодирования, включая
  переводы строк, пустой текст, `$` и кавычки.
- Большие целые в schema values API возвращает десятичными строками.
  `18446744073709551615` нельзя преобразовывать в JS Number. Сохраняйте строку;
  сервер нормализует её в uint64 для Stroppy.
- Используйте `web/src/api/json.ts` для сериализации запросов и JSON-редактора.
  Он отвергает небезопасные числовые литералы; bigint отправляет строкой.
  Нативные отчёты report/baseline/compliance остаются непреобразованным JSON. При
  работе с большими счётчиками внутри этих отчётов нужен lossless JSON parser.

## Диагностика

Fit возвращает `issues[]`; отказ запуска — RFC 9457 Problem с
`validation.errors[]`. Общие поля: `scope`, `path`, `code`, `severity`, `message`.
`input` (также значение при отсутствии scope) адресует входную форму;
`run_spec` — итоговый RunSpec после всех overrides. Индексы массивов нулевые.
Для ошибки общего бюджета `path=machines` означает весь набор машин.
UI показывает ошибку рядом с соответствующим полем/ресурсом, а не разбирает
английское сообщение для восстановления пути. Неизвестные коды показываются
как обычная диагностика с полученной severity.

Пример блокирующей диагностики:

```json
{"scope":"run_spec","path":"machines[0]","code":"capacity_insufficient","severity":"ERROR","message":"insufficient storage"}
```

`ERROR` блокирует исполнение. `WARNING`, включая `capacity_unknown`, означает
ограниченность проверки или недостаточный запас; это не подтверждение
корректности пользовательского SQL. При блокирующей ошибке сохраняются и
сопутствующие предупреждения. Если инфраструктура или схема недоступна,
используется соответствующий Problem; внутренние ошибки не выдаются за Fit.

## Результаты

[result-complete.json](result-complete.json) — синтетический полный native
результат для интеграционного теста. API сохраняет metrics с единицами,
segments, статусы и времена, exit_code, error, errors, compliance, artifacts,
baseline с verdicts/report/error и исходный summary.

Версия Stroppy по умолчанию в каталоге — 6.1.0 (`v6.1.0.63`, JSON-отчёты);
6.0.0 остаётся доступной, закреплённые образы сохранённых тестов не меняются. Исправления из PR Stroppy #173 нужны отдельно
для service-account key auth и полного generated TPC-DS.

Результат содержит необязательные `segments[].report`,
`report_artifact` и `report_omitted`. `report` сохраняет нативный JSON Stroppy
без потери неизвестных полей, новых workload payloads и точности целых.
Исходный файл публикуется через Graphene на 30 дней; ссылка появляется только
после успешной загрузки. Inline-лимит — 64 KiB на отчёт и 256 KiB на run;
превышение объясняется в `report_omitted`, полный файл не обрезается.
Сводка suite имеет собственный общий inline-бюджет 256 KiB: при превышении
оригинал остаётся в дочернем run и его артефакте.
UI загружает большие отчёты через существующий API артефактов сервера.

Поддержка `--report-file` определяется через `stroppy run --help` выбранного
образа. Для старых образов сохранён разбор текстового summary. Образ с поддержкой
JSON обязан выдать report schema 1 / kind run: отсутствие, повреждение или
неподдерживаемая версия делают результат неуспешным, текстовый fallback
запрещён. Чтение ограничено 16 MiB, исходный файл сохраняется и при отказе
разбора. `completed_with_errors` подчиняется прежним thresholds; failed/canceled
сохраняют частичный отчёт. SIGKILL может не оставить файла.
Пайплайн управляет destination/format/enabled отчёта, заменяя одноимённые
extra flags при запуске поддерживаемого образа. Нативный `report.status`
не переименовывается, нормализуется только статус сегмента API.

В компактной карте metrics остаются совместимые имена/единицы (гистограммы
разворачиваются в count/avg/p50/p90/p95/p99). Через нативный report доступны
полные buckets, series и workload-specific payloads. TPS не вычисляется
пайплайном. OTLP остаётся источником временных рядов.
Единственное преобразование статуса: pipeline `canceled` → API `cancelled`.

`result.summary` — headline самого pipeline; `run.summary` — проекция сервера
для списка запусков. Не заменяйте подробный результат этой проекцией.
TPS и throughput берутся из Stroppy. Отсутствие TPS не означает нулевой TPS:
для нетранзакционных нагрузок отображаются queries/s или iterations/s.
Набор metrics и содержимое native reports расширяемы; неизвестные измерения
не отбрасываются. Наличие baseline и compliance зависит от сценария.

Артефакты адресуются `artifact/<id>`. Конфиги сохраняются до явного удаления.
Сроки общей телеметрии остаются прежними: метрики 90 дней, логи 30, трейсы 14.

## Вход, списки и причины ошибок

- `PublicConfig.auth{mode: kratos|dev, kratos{public_url}}`: SPA входит через
  Ory Kratos (`deployments/kratos/README.md`). `Me.email` отсутствует, пока
  адрес не подтверждён в Kratos; клиент не считает его всегда заданным.
- Сортировки списков: `sort` у баз, нагрузок, тестов, запусков (`default`,
  `qps`, `p50`, `p99`, `errors`, `db_kind`, `workload`, `topology`,
  `provider`, `trigger`, `author` …), сьютов, расписаний и ссылок; `order` у
  расписаний и ссылок. Неизвестное значение — 400.
- `RunSummary`: `headline.qps`, `qps_series`, `expected_finish_at`,
  `phase_progress_pct` (необязательные, считаются сервером).
- `PATCH tests/{id}`: флаги `finalize`, `revalidate`; `:rerun` — `resume`.
  `PATCH shares/{id}`: `title`.
- `Problem.reason` и `Problem.params`: стабильный машинный ключ причины
  (`tenant_slug_taken`, `limit_concurrent_runs`, `<сущность>_not_found`) и
  значения для её текста. Клиент показывает свой текст по `reason`;
  `detail` — английское пояснение для неизвестной причины. Ветвиться по
  `code`/`reason`, никогда по `detail`.
- `Me.onboarding{welcome_done, tour_done, checklist_hidden}`; `PATCH /me`
  принимает `onboarding` и сливает флаги по одному.
  `PublicConfig.demo_report_url` — публичный отчёт для первых экранов.
  `GET /tenants/suggest-name?name=` — подсказка от введённого имени.
- Рейтинг сравнивает запуски одного сценария нагрузки (`scenario`: семейство
  скрипта, `tpcc/tx` → `tpcc`) и показывает железо стенда без раннера
  (`HardwareClass`: машины по vCPU и памяти, ключ `2x4c16g+1x2c4g`). Фильтры
  `scenario[]`, `hardware[]`; страница отдаёт варианты, у которых есть запуски.

## Версия и приёмка

Пока контракт `0.x`, его версия идёт вместе с продуктом: сервер, UI и
пайплайны собираются из одного коммита, контракт меняется вместе с кодом, а
релиз, который несёт изменение контракта, поднимает minor (`0.1.0` → `0.2.0`).
`contract_lock.py --write` в `0.x` просто записывает проверенный снимок.
С `1.0.0` ломающее изменение (переименование/удаление поля, смена смысла,
дефолтов, обязательности или семантики merge) требует новой major и
адаптера/миграции сохранённых тестов, а совместимое расширение — minor.

`contract.lock.json` фиксирует схемы, Go входы/выходы, TypeScript-экспорты,
OpenAPI, примеры и происхождение native Stroppy-контракта. CI пересоздаёт
экспорты и проверяет хеши; сама перезапись lock не доказывает совместимость.

После изменения фиксируемых артефактов: генерация, `contract_lock.py --write`,
затем проверки:

```sh
make generate-go generate-ts schemas-export
make contract-check
go test ./... -count=1 -race
(cd pipelines && go test ./... -count=1)
go test -tags=integration ./cmd/... -count=1 -p 1
```

Интеграционная проверка использует PostgreSQL, настоящий HTTP API и
клиентскую TypeScript-сериализацию; Graphene подставной. Она проверяет
сохранение/редактирование/компиляцию, полный результат и структурированный
отказ запуска. Это проверка стыка, а не реальный запуск нагрузки в YC.

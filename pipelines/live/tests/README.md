# Тестовые случаи и результаты

[Единая таблица прогресса](progress.csv) содержит одну строку на сочетание
**БД / версия / топология / workload / preset**. Папки `tpcc-tx`, `tpcb-procs`
соответствуют workloads `tpcc/tx`, `tpcb/procs`.

```text
tests/
  progress.csv
  postgres/17/patroni-ha/simple/smoke-2m-2vus/
    README.md
    case.json
    checks.json
    input.json
    runs/<run-id>/
      manifest.json
      input.json
      result.json
      metrics.json
      logs.json
      ...
  platform/
    catalog/       # общие отчёты о покрытии и оставшаяся область проверки
    suites/        # исходные входы и результаты серий с несколькими БД/тестами
    credentials/   # проверки доступа, без значений секретов
    quotas/
    telemetry/
    lifecycle/
    images/
    history/       # ранние эксперименты и материалы без однозначной привязки
```

## Как читать таблицу

В CSV 16 колонок. Первые пять задают тестовый случай; `execution` отражает
последнее **сохранённое** состояние исполнения. Семь групп содержат результаты
проверок: deployment, workload_check, native_metrics, telemetry, artifacts,
replication, cleanup. `readiness` объединяет обязательные проверки данного
случая. `next_action` показывает ближайшие пробелы, а `details` — путь к
README случая, относительно каталога `tests`.

`passed 5/5` означает пять подтверждённых применимых проверок из пяти.
`unknown 3/5` означает, что три проверки подтверждены, а среди оставшихся есть
недостаточно документированные. `not_applicable` не входит в знаменатель.
При нескольких проблемах приоритет отображения: failed → blocked → unknown → not_run.
Полный список всегда находится в `checks.json` и README случая.

| Статус проверки | Значение |
|---|---|
| passed | Есть ссылка на сохранённое подтверждение |
| failed | Выполненная проверка выявила проблему |
| not_run | Проверка ещё не подтверждена |
| unknown | Сохранённых данных недостаточно |
| blocked | Проверку нельзя выполнить; указана причина |
| not_applicable | Проверка неприменима; указано основание |

Состояние workflow хранится отдельно. `completed` не равняется `passed`.
Дата наблюдения находится в `case.json` и README случая: таблица не выдаёт
исторический снимок за текущее состояние облака.

## Границы покрытия

Перенесены 253 прежние строки и 17 явно обозначенных незапущенных черновиков
(16 PostgreSQL native-export и один пятичасовой Patroni TPC-C).
Черновики требуют нового планирования перед запуском; у них нет завершённых
прогонов и заимствованных успешных проверок.

Готовность отдельного smoke не означает готовность всех пайплайнов. Полные
workload-, baseline-, segment- и fault-матрицы остаются в
[remaining-scope.json](platform/catalog/remaining-scope.json). Их точные параметры
ещё требуется определить; при этом появятся отдельные случаи и строки таблицы.
Проверки histogram/summary-метрик и прочие конкретные незакрытые требования
сохранены в `checks.json`, даже когда они одинаковы для многих строк.

Название preset у перенесённых случаев — историческая метка, а не реконструкция
нагрузки. Фактические параметры доступны в `case.json.actual_segments` и `input.json`.
Ранний генератор мог присвоить общей каталожной строке имя `smoke-2m-2vus`, хотя
подтверждающий прогон использовал другую длительность. История сохранена без
переименования таких случаев и без подмены параметров.

## Что хранится рядом с тестом

- `case.json` — идентичность, выбранная попытка, параметры, ссылки и исходная строка старой таблицы.
- `checks.json` — отдельные проверки, причина статуса, время и ссылка на JSON с указателем на запись.
- `input.json` — публичный снимок входа; он может содержать несколько сегментов одного исходного прогона. Это не команда запуска только выбранного workload.
- `runs/<run-id>/` — результаты конкретной попытки и её manifest. Вход сохраняется отдельно от будущих настроек случая.
- `history/`, если присутствует, — ранние попытки, не используемые как текущее подтверждение.

Если один прогон содержал несколько workloads, файлы хранятся один раз.
Другие случаи используют относительную ссылку `runs/<run-id>` на ту же папку.
Доступные ранние результаты с неоднозначной идентичностью остаются в `platform/history`,
пока их нельзя достоверно связать с конкретной попыткой.

Версии образов, интервалы наблюдений, счётчики retry и диагностика остаются
в материалах прогона и исходных отчётах. Новая сборка не наследует подтверждение
предыдущей автоматически. Входы без приватных OTLP-заголовков не восстанавливают
секреты и не являются точной копией приватного запроса.

В 16 повторно используемых входах исправлены пустые исторические заглушки
заголовков OTLP, не соответствовавшие схеме: удалено пустое `observability.headers`
или заменён пустой объект `otlp_headers` на пустую строку. Изменения перечислены
в [input-normalization.json](platform/migration/input-normalization.json) и
`case.json.input_transformations`. Исторические входы прогонов и исходные suites
сохранены без изменений. Все 270 входов случаев проверяются по `spec.run@1`.

## Обновление

Добавить или обновить `case.json`, `checks.json` и материалы попытки, затем
из корня репозитория выполнить:

```sh
python3 pipelines/live/tools/live.py progress
```

CSV и README случаев генерируются автоматически. Проверка перед генерацией
контролирует пути, ссылки на evidence, JSON pointers, идентичность попыток,
наличие обязательных групп и целостность перенесённых материалов.

Старые имена сохранены в [карте переноса](platform/migration/paths.json).
Их также понимает команда `python3 pipelines/live/tools/live.py resolve <старое-имя>`.
Содержимое исторических JSON сохранено побайтово; старые пути внутри них
разрешаются через эту карту. Пути к приватным `/tmp`-каталогам описывают историю
и не означают наличие этих файлов в репозитории.

[Исторические подробности](platform/history/README.md) сохраняют контекст прошлых
проверок и не определяют актуальную версию кластера или команды работы.

## Dev-сборки Stroppy

Часть доказательств относится к временным dev-образам. Исправления опубликованы
в [Stroppy PR #166](https://github.com/stroppy-io/stroppy/pull/166).
Официальный образ заменит dev-образы после слияния, публикации и повторных
проверок. Для каждой сборки сохраняются digest, хеш бинаря и доступная информация
об исходниках; последний коммит PR не восстанавливает все промежуточные сборки.
